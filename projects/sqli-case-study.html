SQL INJECTION: LAB TO REAL WORLD

// From Structured Practice to Exploiting a Financial Application During VAPT

SQL INJECTION MANUAL EXPLOIT BURP SUITE SQLMAP VAPT FINANCIAL SECTOR IN PROGRESS
00 // OVERVIEW

During a Web Application VAPT engagement for a financial services platform, a SQL Injection vulnerability was identified in a loan processing endpoint. The vulnerability allowed execution of arbitrary SQL queries through an unsanitised numeric parameter (loan_id).

This case study demonstrates the transition from structured lab learning on PortSwigger Web Security Academy to real-world exploitation and professional reporting. All client details are fully anonymised per NDA obligations.

Manual testing revealed an exploitation path that automated scanners failed to detect — the endpoint was JavaScript-rendered and not crawled during initial automated assessment.

01 // DISCOVERY PHASE

While intercepting traffic in Burp Suite, the following endpoint was identified during authenticated session testing of the loan management module:

// IDENTIFIED ENDPOINT
GET /api/loan/pending?loan_id=1023 HTTP/1.1 Host: [redacted] Authorization: Bearer [token]

Modifying the parameter with a single quote to test for injection:

// INJECTION TEST
loan_id=1023'

Returned a verbose SQL syntax error — confirming:

  • Backend SQL query concatenation without sanitisation
  • Lack of input validation on numeric parameter
  • Verbose error messages exposing DB internals
  • Injection point confirmed
📸 Figure 1 — SQL error confirmation via Burp Suite (Screenshot sanitised — client identifiers removed)
02 // INJECTION VALIDATION

Manual testing confirmed the endpoint was vulnerable to three injection types:

  • Error-Based SQL Injection — verbose DB errors returned in response
  • Boolean-Based Blind SQL Injection — different responses for true/false conditions
  • Time-Based Blind SQL Injection — measurable delays via sleep functions
// BOOLEAN-BASED TEST
-- True condition → normal response loan_id=1023' AND 1=1-- -- False condition → empty/modified response loan_id=1023' AND 1=2--
// TIME-BASED TEST
-- 5 second delay confirms vulnerability loan_id=1023' AND SLEEP(5)--

The application returned HTTP 200 responses even with injected payloads, indicating no WAF or input-level validation was in place.

📸 Figure 2 — Modified request returning HTTP 200 with injected payload (Sanitised)

If exploited by a malicious actor, this vulnerability could enable:

  • Extraction of borrower personally identifiable information (PII)
  • Unauthorised access to KYC documentation
  • Manipulation or deletion of loan records
  • Financial fraud through data tampering
  • Complete service disruption via destructive queries

In a regulated financial environment, this exposure could result in:

  • Regulatory non-compliance (RBI, GDPR, PCI-DSS)
  • Mandatory breach notification obligations
  • Legal liability and financial penalties
  • Irreversible reputational damage
  • Loss of customer trust and platform credibility

06 // ROOT CAUSE

The vulnerability was caused by dynamic SQL query construction where user-controlled input was directly embedded into the query string without parameterisation or sanitisation:

// VULNERABLE CODE (JAVA)
// ❌ VULNERABLE — direct string concatenation String query = "SELECT * FROM loans WHERE loan_id = '" + loan_id + "'"; Statement stmt = conn.createStatement(); ResultSet rs = stmt.executeQuery(query);

Numeric parameters are frequently overlooked during input validation implementation. Developers often assume integer fields are safe without explicit type enforcement — this assumption is incorrect and dangerous.

07 // REMEDIATION

Primary Fix — Parameterised Queries (Prepared Statements)

// SECURE CODE (JAVA)
// ✅ SECURE — parameterised query PreparedStatement stmt = conn.prepareStatement( "SELECT * FROM loans WHERE loan_id = ?" ); stmt.setInt(1, loanId); // enforces integer type ResultSet rs = stmt.executeQuery();

Additional Defensive Measures:

  • Enforce strict numeric validation for loan_id — reject non-integer input at API layer
  • Disable verbose SQL error messages in production — use generic error responses
  • Enforce least privilege database access — application user should not have DDL rights
  • Deploy WAF rules for SQL injection pattern detection as defence-in-depth
  • Implement centralised input validation across all API endpoints
08 // PROFESSIONAL LESSONS LEARNED
01
Numeric parameters are frequently overlooked during validation — always test integer fields for injection, not just string inputs.
02
Manual testing revealed exploitation paths completely missed by automated scanners due to JavaScript-rendered endpoints.
03
